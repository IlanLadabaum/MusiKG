# Data Source R&D

Scope: choose data sources for recording-centered discovery by measuring their correct, usable contribution on the same varied test set. This is research, not an application implementation plan. The [earlier survey](Research%20-%20Existing%20Projects%20and%20Data%20Sources.md) and its 12-recording MusicBrainz probe are exploratory evidence, not the benchmark.

The [source capability audit](Source%20Capability%20Audit.md) compares documented fields, query precision, access and provisional relationship types before benchmark design. It reports claims made by documentation, not measured coverage.

## Decisions and open questions

- [DECIDED] Inventory as many plausibly useful free sources as practical before choosing a primary source or supplements. Include credits, identity, works/writers, labels, covers/samples and relevant context.
- [DECIDED] Build a 500-recording, wide-ranging tagged test set and measure each source's unique contribution and the combined contribution. Choose the actual app sources only after this analysis. Report results by genre, country/region, era and other relevant strata, and create narrower follow-up sets where gaps appear.
- [DECIDED] Offline graph availability is optional during source evaluation. Revisit storage, refresh and offline querying after examining the best data and its terms. This does not change the local computation/no hosted application infrastructure goal.
- [DECIDED] Optimize first for an accurate, information-rich graph. Preserve semantically distinct relationship types so graph views and ranking can filter or weight them later; do not preemptively discard entire categories of information because they seem less central to version 0.
- [DECIDED] Free registration, API keys or one-time provider approval are acceptable candidates. Record the setup and user experience cost in practicality rather than excluding them in advance.
- [DECIDED] Collect release-level associations and preserve their source scope. Benchmark them separately from claims that a person worked on a particular recording. [OPEN] Decide later whether the graph uses release nodes, scope properties, or another encoding.
- [DECIDED] Use five era strata for corpus analysis: before 1950; 1950–1969; 1970–1989; 1990–2009; and 2010–2026. Allocate 100 recordings per era: 90 general cases plus 10 deliberately difficult identity cases. The developer approved this allocation; exact membership remains open.
- [IN PROGRESS] A [500-row candidate draft](Corpus%20Draft/500-recording-candidates.tsv) now follows that allocation. Its [readme](Corpus%20Draft/README.md) records local checks. The structural query check passes; the list is not yet frozen. Only 23 generated candidate rows have independent evidence links, while the separate identity-review worksheet has 45 verified, 4 ambiguous and 451 unreviewed rows. Full independent verification is **not** required to ask what the APIs return. The developer explicitly deferred the actual source benchmark.
- [IN PROGRESS] The [benchmark handoff](Benchmark%20Handoff.md) specifies input freeze, source eligibility, run data contract, query pilot, analysis outputs and next-agent sequence. A structural query checker and optional deep identity-review checker exist. This is preparation only, not a completed source run.
- [OPEN] Final source selection, source order, data-merging rules, exact membership of the 500-recording benchmark, and whether any source with registration or free personal-use restrictions fits a public open-source app.

## Research stages

1. **Candidate capability audit.** Before benchmark design, compare each source's documented entity/field inventory, relationship semantics, lookup/search/filter granularity, identifiers, API/dump availability, authentication, rate limits, costs, licensing/retention/redistribution rules and maintenance. Identify where a narrowly targeted request could fill a missing property without repeating broad queries. Build a provisional cross-source type map while retaining raw source roles and their recording/work/release scope. Separate free access from permission to integrate into a public app. Mark inaccessible sources as such rather than silently excluding them. See [Source Capability Audit](Source%20Capability%20Audit.md) when completed.
2. **Test corpus.** [DECIDED] Use 500 specific recordings with tags enabling fine-grained analysis by genre, country/region, era and other meaningful categories. [PROPOSED] Record title, artist, release/version, year, duration and available IDs. Stratify across mainstream and independent releases, genres (pop, rock, hip-hop, jazz, classical, electronic, folk, country, Latin, global traditions), live/studio, covers/remixes/reissues, collaborations, physical/digital-first releases and obscure tracks. Include deliberately difficult identity cases. Define country tags carefully (artist origin, recording location and release market are different). Choose exact membership with the developer before locking the corpus. Keep a separate small representative personal-library sample if available; do not publish private listening history.
3. **Evidence collection.** Query each eligible source against the same recording/version. Preserve source record URLs/IDs, raw credit text, role, scope (recording, track, release, work), retrieval date and any identifiers. Document failures, missing records and access limitations. Do not assume that a release-wide credit applies to every track.
4. **Human verification.** Check matched versions and a sample of extracted claims against source pages/liner notes or independent references. Mark confirmed, plausible, ambiguous, contradicted, and unresolved. Missing data is not evidence that a credit does not exist. Resolve disagreements with the developer when they determine attribution policy.
5. **Contribution analysis.** Report per-source match rate and *correct* coverage by useful relationship type: performers/instruments, producer/engineer, writer/composer, work/cover/sample, label/release, and contextual facts. Compute the union across sources, each source's exclusive correct claims, and its marginal lift when added to other plausible source combinations. Report duplicates and errors separately so a verbose source does not win by producing more unverified edges. Stratify results; an aggregate score alone would hide genre/era gaps.
6. **Practicality analysis.** For each source, measure calls/time per 100 recordings, rate-limit and outage behavior, local disk/cache needs, mandatory credentials, terms affecting persistence/offline use, cross-platform feasibility and maintenance burden. Record total build time by input size and source combination so later loading-page estimates can be grounded in observed performance. Exclude sources that are not lawful or practical for the intended app even if the data is attractive; record them as research-only comparators.
7. **Decision review.** Present a source matrix and sample evidence with recommendations for a seed source set, conditional enrichers and a provisional graph type model. Compare broad enrichment with on-demand, missing-property requests where source APIs support them. The developer chooses the source strategy and model after the full analysis; only then settle source-specific matching, conflict and graph rules.

### Inventory boundary

- [PROPOSED] Benchmark machine-accessible and permission-compatible sources quantitatively. Keep manually searchable or restricted sources in a separate reference tier for validating sampled claims. A free webpage should never be scraped merely because it is visible.
- [PROPOSED] Measure identity resolvers, credits, work rights, cover/sample links and descriptive context as distinct source roles. A source that only resolves an ISRC can be essential even if it contributes no graph credit edges.
- [OPEN] Confirm whether provider catalogs (Apple Music, Deezer, TIDAL, etc.) add usable non-obvious credit fields under free developer access; they may be input/identity bridges rather than enrichment sources. Their current terms and API fields require a separate official-documentation pass.
- [OPEN] Discogs dump extraction practicality, MLC account/API terms and SoundExchange API eligibility are consequential access checks for their respective benchmark routes. They do not block the 500-recording corpus or other open-source runs. CISAC's paid third-party ISWC API is excluded from the free-source benchmark; its limited open-data mapping is a separate candidate.

## Measurement definitions to settle before querying

### Proposed benchmark design for review

- [PROPOSED] Select the 500 recordings from sources independent of the databases being scored, plus a deliberately curated hard-case panel. Do not require a MusicBrainz, Discogs, Spotify or other scored-source ID for admission: doing so would inflate that source's apparent match rate. Confirm the *specific recording/version* using independent evidence where possible, then attach IDs as observations rather than selection criteria.
- [DECIDED] Use a broad diagnostic frame rather than claim a representative sample of all music: 100 items in each of the five eras, with 90 general and 10 hard identity cases per era. Cross-stratify over regions and broad genre families where historically applicable. Use multiple tags when genres overlap. Log each nomination route. Exact membership requires developer review before the corpus is locked.
- [PROPOSED] Within each era, build a candidate pool from several independent, dated sources such as contemporary release lists, library/catalog records, public-domain historical discographies and local/regional music histories. Record the source of each nomination. Choose from that pool using predeclared quotas for broad genre, region, popularity and release format, then inspect and replace duplicate or incorrectly identified recordings *before* querying any source under evaluation. Add a separately labeled hard-case subset by deliberate selection; do not describe it as random.
- [PROPOSED] Cap repeated artists and releases in the general sample (for example, two recordings per artist and one per release) to prevent one exceptionally documented album or superstar from dominating. Allow explicit exceptions in the hard-case subset, such as two distinct versions of the same work. This cap needs developer review.
- [PROPOSED] For each candidate, record title, credited performers, version cue, approximate first release date, and a public evidence link independent of the scored source when available. If the evidence identifies only a work or an album rather than a particular sound recording, flag it for resolution before inclusion. Do not silently substitute a convenient database match for the intended recording.

#### Concrete nomination and selection procedure [PROPOSED]

1. Make a nomination pool larger than 500, with independent origin links and *no requirement* that any evaluated database already has the recording. Use several kinds of lists: dated chart archives for commercially visible releases; institutional sound catalogs and preservation lists for older or regionally important recordings; and targeted specialist collections for less-commercial styles. Examples of candidate lists include [Official Charts' public history](https://www.officialcharts.com/songs-albums/) (UK popularity, with [licensed chart data](https://www.officialcharts.com/our-business-services/chart-licensing/) kept out of the research dataset), the [Smithsonian Folkways catalog](https://folkways.si.edu/catalog) and its [regional/era browsing](https://folkways.si.edu/world), and [BnF/Gallica historical audio collections](https://www.bnf.fr/fr/les-fonds-sonore-du-departement-son-video-multimedia-accessibles-sur-gallica). These sources themselves have selection and geography biases; log nomination route and avoid any one list dominating. The [Library of Congress National Recording Registry](https://www.loc.gov/programs/national-recording-preservation-board/recording-registry/complete-national-recording-registry-listing/) is a useful example of a preservation list, but using it to choose items would favor the Library of Congress source in the benchmark; either omit it as a seed or report its seeded rows separately in LoC results.
2. Within each decided era, allocate 90 general cases plus 10 explicitly difficult identity cases. In the general cases, mix prominent and obscure recordings rather than using only charting music or only archival material. Genre and region are overlapping tags, with per-cell counts published before source testing; do not require equal genre counts in eras before the genre existed. This yields a diagnostic stress test, not an estimate of the world's actual music distribution.
3. Confirm the intended *sound recording*: performer and version; original release or session evidence; an approximate first-recording or first-release date with the date type indicated; and, where available, duration/format or catalog number. Album-only and composition-only nominations are unresolved until a track/performance is specified. If a 2020 remaster uses the same underlying recording, record both the original recording era and the reissue date rather than reclassifying it as a 2020 recording.
4. Apply artist/release concentration caps proposed above to the general sample; record every exception. Replace invalid nominations from the same era/region/genre/popularity cell using a reserve list selected before scored-source lookup. Never replace a recording because MusicBrainz, Discogs or another evaluated source lacks it; that absence is an outcome.
5. Prepare a draft manifest in the repo with the 500 proposed recordings, tags, nomination evidence and unresolved identities for developer review. Freeze the accepted version before querying scored sources. Keep the hard-case panel and any source-seeded exceptions identifiable in every analysis table.

**Current stage:** prepare a full draft corpus under the approved allocation. Exact song membership remains reviewable and open; no source benchmark runs until the developer separately authorizes testing.
- [PROPOSED] Define region primarily as the recording's artistic/cultural origin, with separate fields for artist origin, recording location, language and release market. Permit `unknown` and multiple regions; never infer a single country from a streaming-store territory or a label address. For multi-region collaborations, use multi-label tags and report overlaps rather than forcing one country.
- [PROPOSED] Freeze a corpus manifest before examining source outcomes. Record inclusion/exclusion rationale, identity evidence and a versioned manifest hash. A later focused follow-up set is reported separately, not quietly added to the original 500.
- [PROPOSED] Run all eligible sources over the same frozen corpus, but allow source-specific queries. Keep a query plan for each source and log every candidate match. Score retrieval and identity resolution separately from credit extraction so a source is not rewarded for credits from the wrong recording.
- [PROPOSED] Compare claims only after normalizing subject identity, target identity, role and scope. Report exact duplicates, near-equivalent role names, version mismatches and cross-source disagreements separately. Preserve raw role labels and release/work/recording scope so the provisional type map can be revised.
- [PROPOSED] For correctness, audit a stratified sample of single-source claims, multi-source agreements, conflicts and likely version errors. Prefer independently attributable evidence, such as release liner notes or creator/label statements. Report the adjudicated sample size and unresolved share for every claim family; do not call absence in another database a false claim.
- [PROPOSED] Report per-source eligibility before coverage: open machine access; conditional/free registration; research-only/manual comparator; paid/excluded. A source that cannot be called or retained under its terms gets a recorded access outcome, not an assumed zero-coverage score.

- [PROPOSED] Evaluate **recording match** separately from **credit availability**. A correct credit on the wrong version is a failure for this product.
- [PROPOSED] Count normalized claims (entity + relationship + target + scope) rather than raw fields. Keep raw data and evidence so normalization can be revised.
- [PROPOSED] Measure both exclusive contribution (only one source supplies a verified claim) and marginal lift in combinations, because sources overlap; no single source order should predetermine the result.
- [PROPOSED] Show uncertainty intervals or raw numerator/denominator per stratum, not just percentages, particularly for niche categories.
- [OPEN] Exact threshold for keeping a source: coverage lift, novelty for ranked discoveries, access/reliability and implementation cost should all count; the developer will set priorities after seeing results.

## Evaluation data to retain

- [DECIDED] Keep a queryable per-recording, per-source research dataset of everything a source returns that could matter for coverage or subsequent analysis. Preserve raw responses or source snapshots **only where source terms allow**; otherwise retain permitted IDs, URLs, metadata and evaluation notes. Version the extractor and record retrieval date so results can be reproduced or compared after source updates.
- [DECIDED] If a response can be received but cannot be retained, record that it was received, what query produced it, its status/size/timing, which permitted aggregate or derived observations were made, and the applicable retention restriction. Such a source may still support online, transient enrichment but cannot by itself support a permanent offline graph; verify the actual terms before making either assumption.
- [PROPOSED] Corpus row: benchmark ID; canonical title and aliases; credited artist(s); album/release/version; duration; dates; ISRC/ISWC/MBID/provider IDs when independently verified; genre tags (possibly multiple); artist country/region and language; release era; popularity tier; recording type (studio/live/remix/etc.); and evidence URL for identity. Mark unknown tags rather than guessing.
- [PROPOSED] Query log: source and endpoint/dump version; input sent; candidate IDs and scores; request start/end and latency; retries, rate-limit waits, HTTP errors; bytes and payload size; parser version; operator interventions. Include per-recording wall time, total elapsed time and useful validated claims per second, but do not use throughput alone as a quality metric.
- [PROPOSED] Claim row: benchmark ID; source record ID/URL; subject and target IDs/names; raw role/value; normalized role/value; recording/work/track/release scope; claimed date/location where relevant; confidence/match rationale; evidence pointer; human-review status; and any conflicting claim IDs. This keeps detailed coverage available for later questions.
- [PROPOSED] Correctness: use cross-source agreement to **prioritize review**, not as ground truth, because sources may copy one another or share the same wrong release attribution. Hand-audit a stratified subset (including agreements, disagreements and single-source claims) against original liner notes, artist/label credits or other independent evidence where available. Report recording-match precision separately from claim precision, plus unresolved rate and inter-reviewer disagreements. Treat unverified as unverified, not false. A full gold standard for all credits on 500 recordings is unlikely, so coverage is observed coverage rather than recall of all real-world credits.
- [PROPOSED] Practicality scorecard: access and eligibility (free/registration/permission), rate limits and reliability, developer setup effort, identity-matching difficulty, requests and elapsed time per 100 recordings, disk/storage/retention restrictions, attribution obligations, portability and ongoing maintenance. Use qualitative notes plus measured quantities rather than one opaque numeric score.

## Vision questions that could change source selection

- [DECIDED] Collect any information that can form an accurate, meaningful graph relation, including people, labels, studios, places, genres and work/cover/sample links when available. Determine ranking, UI emphasis and pruning after seeing the data.
- [DECIDED] Release-level credits belong in the collected information, with their original scope retained. Do not silently promote them to recording credits. [OPEN] Choose the graph representation after source results and examples are reviewed.
- [DECIDED] Free registration, API keys and one-time approval are acceptable to investigate; include their setup and per-user feasibility in practicality. A public app cannot assume the developer's personal research access grants every user access.
- [OPEN] Is the first-release audience global across languages and traditions, or is there a narrower target despite the broad benchmark? The 500-recording set can be broad either way, but weighting the final source choice depends on intended users.
