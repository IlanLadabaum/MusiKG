# Research — existing projects and music data sources

Research snapshot: 2026-10-10. Scope: find an existing open-source product or reusable components, and assess free/open sources for recording-level credits and related graph data. Findings below are research, not product decisions. Source policies and project licenses should be checked again before implementation.

## Product lens

- [DECIDED] The general user experience leads with explainable discoveries from a user's song list; graph exploration is an additional mode.
- [DECIDED] The app is local-first, cross-platform, and uses specific recordings as input. Network access while building or extending a graph is acceptable.
- [OPEN] Whether completed graphs must remain fully usable offline, and how cached third-party metadata is refreshed.
- [OPEN] Source conflict and uncertain-match presentation; revisit after testing specific sources.

## Comparable open-source projects

No reviewed project implements the full intended flow of **arbitrary weighted recordings → comprehensive credited-person graph → ranked, explainable hidden influences → lightweight local desktop app**. This is a conclusion about the projects reviewed below, not a claim that no such project exists.

| Project | Relevant parts | Fit / reuse assessment |
| --- | --- | --- |

It ingests entire database dumps into Neo4j and PostgreSQL with multiple services; its documented Discogs dump is about 11.3 GB compressed. That conflicts with the intended lightweight personal installation. - [DECIDED] The developer's existing graph explorer is unsuitable as a fork.

## Candidate metadata sources

| Source | Data and identity fit | Access and constraints | Initial assessment |
| --- | --- | --- | --- |
| [MusicBrainz](https://musicbrainz.org/doc/MusicBrainz_Database) | First-class recording, work, release, label, artist, instrument, and relationship entities. Recordings can have ISRCs; works can have ISWCs. Typed relationships cover performers, producers, writers, and more. | [Public API](https://musicbrainz.org/doc/MusicBrainz_API) supports ISRC lookup and recording/work/release relationships without an API key, but requires a meaningful User-Agent and at most [one call per second per client](https://musicbrainz.org/doc/MusicBrainz_API). Discogs distinguishes main release credits from track-specific credits, so projecting an album-level credit onto every track could be wrong. | The [official dump landing page](https://data.discogs.com/) labels the monthly XML dumps CC0; the October 2026 releases file is about 10.5 GB compressed. The distinct [API terms](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use) impose attribution, storage and freshness requirements. | [OPEN] Potential credit supplement. Test selective dump extraction and its unique contribution; assess API integration separately under its terms. |
| [Wikidata](https://www.wikidata.org/wiki/Wikidata:Licensing) | General linked data: artists, works, labels, places, dates and external IDs. MusicBrainz documents [MBID links](https://musicbrainz.org/doc/Wikidata), making entity-level enrichment possible. | Structured data is CC0; query service/API and dumps are described in [Wikidata data access](https://www.wikidata.org/wiki/Wikidata:Data_access). Public query service is shared infrastructure, so avoid broad recursive queries per user. | [PROPOSED] Optional context and cross-database links, not the main session-musician credit source. Its general-purpose schema does not itself establish recording-credit coverage; benchmark it. |
| [Spotify Web API](https://developer.spotify.com/documentation/web-api/reference/get-track) | Spotify track object includes provider ID, artist and album data, release date and `external_ids.isrc`. | Requires OAuth and compliance with Spotify platform policies. It is a useful input bridge but the documented track object does not contain comprehensive session musician or producer credits. | [PROPOSED] Adapter for Spotify tracks → ISRC/candidate MusicBrainz recordings. Do not make Spotify IDs the graph's only identity. Research playlist/history access separately. |
| [TheAudioDB](https://www.theaudiodb.com/free_music_api) | Artist, album and track lookup, some artwork and descriptive data, lookup by MusicBrainz IDs. | Free v1 API advertises [30 requests/minute](https://www.theaudiodb.com/free_music_api); v2 is premium. Some ListenBrainz listens have no MBID. |

### MusicBrainz modeling details that matter

- The [API's relationship includes](https://musicbrainz.org/doc/MusicBrainz_API) can traverse recording → work → writer, but a recording lookup needs both `work-rels` and `work-level-rels` plus `artist-rels` to retrieve the work's artist relationships. Release/label data may require additional queries.
- A Spotify track has an ISRC field, and the MusicBrainz ISRC endpoint returns a **list** of recordings. Therefore ISRC is a strong candidate key, not a guaranteed one-to-one mapping. Title, artist, duration, release and version cues may still be needed.
- The [MusicBrainz relationship statistics](https://musicbrainz.org/statistics/relationships) show substantial artist-recording links, but relationship counts do not tell us what share of a user's songs have producer, performer, or writer credits. Avoid presenting database size as coverage.
- Discogs track credits are release-specific. A recording can occur on many releases, and an album-level credit may not apply to every track. Preserve the source release and credit scope instead of flattening all credits onto a recording.

Credit categories below reflect the **manually selected candidate**, not automatic end-to-end import. This was a convenience sample of famous recordings, so its rates are not a forecast for users' libraries. Results: after manual candidate selection, 9/12 had at least one instrumentalist relationship, 10/12 a producer relationship, and 11/12 a linked work with a writer/composer/lyricist relationship. The naive first search hit had any recording-level personnel credit on only 6/12. At least five first hits were clearly a later or different version by title, date, or duration. These are small-sample observations and partly reflect manual selection of richer records; they do **not** establish automatic matching accuracy or population-wide credit coverage.

For an additional identity check, ten selected ISRCs were looked up through MusicBrainz. Seven returned one recording and three returned two (Superstition, Get Lucky, Alright). The eleventh lookup was interrupted by a transient HTTP 503; So What's chosen 1959 record had no ISRC. ISRC is valuable but does not guarantee a unique MusicBrainz recording. An application needs conservative tie-breaking and an unresolved state. Requests were paced over one second apart, yet a 503 still occurred, so retry/backoff is necessary.

This probe did not authenticate to Spotify or verify that Spotify's ISRC for any specific track equals the selected MusicBrainz ISRC. It did not perform a like-for-like Discogs comparison; that still needs release matching, source-use review, and a defensible way to assign release-level credits to tracks.

## Checks on the additional research pass supplied by the developer

- [VERIFIED] Spotify's [February 2026 Development Mode guide](https://developer.spotify.com/documentation/web-api/tutorials/february-2026-migration-guide) says new development apps require an owner with Premium, allow five users, expose playlist items only for playlists the user owns or collaborates on, and remove batch track fetch. It says `external_ids` was restored; Spotify's [track reference](https://developer.spotify.com/documentation/web-api/reference/get-track) still documents ISRC. The [quota-mode policy](https://developer.spotify.com/documentation/web-api/concepts/quota-modes) makes ordinary public-scale API onboarding a major constraint. This changes the priority of export-based import research.
- [VERIFIED] Spotify's [description of Extended Streaming History](https://support.spotify.com/us/article/understanding-your-data/) says it spans the lifetime of the account and includes track URI, play duration, timing, skip, shuffle, and start/end reasons. It also contains sensitive fields such as IP address, which an importer would have no need to retain. The supplied claim about a particular export turnaround was not confirmed.
- [VERIFIED WITH CAVEAT] MusicBrainz provides twice-weekly database snapshots, including a [PostgreSQL-oriented core dump](https://musicbrainz.org/doc/MusicBrainz_Database/Download). A [JSON dump index](https://ftp.musicbrainz.org/pub/musicbrainz/data/json-dumps/20261007-001001/) also exists; the October 7 release lists a 22 GB compressed `release.tar.xz`, a clear warning against bundling full dumps in a lightweight app. The claim that JSON dumps omit particular work relationships remains unverified and should not determine architecture yet.
- [PARTLY VERIFIED] Discogs documents release and per-track credits and identifies catalog credits as CC0 in its [API terms](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use). A later check of the [official dump landing page](https://data.discogs.com/) confirmed the monthly XML dumps are labeled CC0. Selective extraction and a sustainable offline-graph route remain untested.
- [DEFERRED] [LRCLIB](https://github.com/tranxuanthang/lrclib) is a lyrics service, not a credit source. The claim of *no rate limiting* is unsafe: its maintainers discuss active rate limiting in a [project discussion](https://github.com/tranxuanthang/lrclib/discussions/91). Lyrics rights and usefulness for this product need separate scoping; no reason to make lyrics part of version 0 yet.
- [OPEN] Genius credit/sample APIs and Last.fm/ListenBrainz/other-service import methods warrant a later access and licensing review. ListenBrainz does offer a [recording MBID mapper](https://mapper.listenbrainz.org/docs), but not every listen is guaranteed to have a recording MBID.

## Provisional direction and validation

### Industry-wide credits and a combined-source approach — 2026-10-10

- [RESEARCHED] The industry shares credits through standards and private feeds rather than one complete, freely queryable credits registry. [DDEX RIN](https://kb.ddex.net/implementing-each-standard/recording-information-notification-%28rin%29/rin-faq/) standardizes capture/exchange of recording contributors and roles; it is a message format, not a public corpus. The [IFPI ISRC database](https://isrc.ifpi.org/) is a large public recording-identity search, but its documented minimum fields are artist, title, version, duration and publication date, not session personnel. Its coverage is not universal because distributors may not register every assigned ISRC there ([IFPI FAQ](https://isrc.ifpi.org/faqs)).
- [RESEARCHED] [Jaxsta's API documentation](https://apidocs.jaxsta.com/) describes a licensed, industry-supplied collection of 240 million credits across 44 million recordings and 10 million works. It offers subscription plans and test credentials by request, so it may have better official credit depth, but it is not a free/open default backend. The counts are provider claims, not measured coverage of our input library.
- [RESEARCHED] The US [MLC Public Search API](https://www.themlc.com/hubfs/The%20MLC%202024%20Annual%20Report.pdf) serves musical-work ownership information. It could help resolve writers/publishers but not recording-session players; access terms and international scope need review before use. [Wikidata](https://www.wikidata.org/wiki/Wikidata:Licensing) remains a CC0 source for cross-identifiers and artist/label context.
- [HISTORICAL PROPOSAL] MusicBrainz as an identity spine with Discogs and Wikidata enrichment was suggested before the developer chose a source-neutral benchmark. Do not treat this as the preferred architecture; use the [Data Source R&D plan](Data%20Source%20R%26D.md) to choose sources from measured evidence. Preserve source, scope and uncertainty as evaluation data.
- [OPEN] Test whether selective local extraction from the [CC0 Discogs dumps](https://data.discogs.com/) is practical; the October 2026 releases file is about 10.5 GB compressed. Its distinct [API terms](https://support.discogs.com/hc/en-us/articles/360009334593-API-Terms-of-Use) impose six-hour display freshness and storage limits, which complicate an indefinitely offline graph built directly from API content. Seek explicit clarification if necessary. Measure its unique, correctly scoped credits in the source-neutral benchmark. Full catalog dump processing is too heavy to require of ordinary users.
- [DECIDED] Source choice follows a broad inventory and like-for-like benchmark. Detailed matching and graph rules follow that choice. Paid feeds can be listed as comparators but are outside the initial free-source search.

- [HISTORICAL PROPOSAL] Spotify ISRC → MusicBrainz recording lookup was an initial candidate route; the source-neutral benchmark will compare identity and credit contributions before selecting a route. Show unmatched songs and missing credit categories rather than treating missing data as a negative fact.
- [DECIDED] Evaluate multiple free sources on the same broad corpus and measure each source's unique and combined contribution; see the [Data Source R&D plan](Data%20Source%20R%26D.md).
- [OPEN] Run a representative, hand-checked sample across mainstream, independent, older, live, remix and cover recordings. For each source measure (a) identity match rate, (b) precise session-musician/producer/writer credit coverage, (c) incorrect attribution, (d) requests/time per 100 songs, and (e) local cache size. Use those results to choose sources and matching policy.
- [OPEN] Decide whether graph output stores third-party data permanently, how provenance is shown, and whether data can be exported or shared. Offline graph use may be deferred to gain access to better sources.
