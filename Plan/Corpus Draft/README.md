# 500-recording candidate draft

This is a **provisional nomination list**, not the frozen benchmark corpus. The developer approved the five-era allocation of 100 candidates each (90 general, 10 deliberately difficult) and deferred the actual database test. No candidate-source API or dump has been queried to build or score this list. The benchmark measures what sources return for these inputs, including no matches and wrong matches; independent verification of all 500 recordings is not a prerequisite.

`era1.txt` through `era5.txt` are the editable nominations. `build_manifest.py` combines them into `500-recording-candidates.tsv` and checks row counts, era ranges, and exact artist/title duplicates. The TSV is the review view. IDs are draft row numbers; they will change if rows are replaced or reordered.

`recording-review.tsv` is the ID-aligned optional identity-review worksheet. It was prefilled with nomination hints, **not verified facts**. Set `identity_state=verified` only after checking the intended sound recording and completing all required fields; `evidence_scope=exact_recording` means the linked evidence distinguishes that recording. `make_review.py` generates a new worksheet and refuses to overwrite an existing one. If candidate rows change, preserve existing reviews and reconcile IDs manually rather than regenerating over them. `check_readiness.py` reports deep review progress, but its nonzero exit does **not** block source queries. `check_query_readiness.py` is the structural input check. Neither script can judge whether differently named entries are the same recording.

`collect_apple_identity_leads.py` is a separate corpus-research helper. It queries Apple's public [iTunes Search API](https://performance-partners.apple.com/search-api) at 3.5-second spacing (the documented limit is approximately 20 calls/minute), logs selected catalog facts and URLs in `apple-identity-leads.tsv`, and resumes by candidate ID. Apple is **not** one of the scored enrichment sources in this benchmark. An Apple result is a *lead*, never automatic verification: a catalog release date may describe a reissue, a title match may be a cover/live take, and absent results say nothing about whether a historical recording exists. The script does not retain raw JSON, images or previews. Reviewers must examine the result, its specific version and independent evidence before marking any row verified. `triage_apple_leads.py` scores name similarity for reviewer attention only; its `possible_match` state does not verify identity.

The optional Apple lead scan was stopped after 314 unique input IDs (305 returned results, 8 returned no results, 1 errored). It is resumable, but completing it is not needed before the scored-source benchmark and would privilege Apple-catalog availability in a source-neutral input set.

The `artist_hint`, `title_hint`, `year_hint`, `origin_hint`, and `genre_hint` columns are **hints**, not verified recording metadata. A linked source may establish only a title, performer, or release rather than the precise recording/version. `evidence_linked_version_pending` therefore does not mean identity verified. `curated_preliminary` means a human-readable nomination from preliminary research and memory, not a random sample or a documented nomination route. The `hard` cohort intentionally contains ambiguous identities, alternate versions, reissues, and similar cases; ambiguity should be measured and adjudicated where possible, rather than used to exclude these inputs automatically.

**[DECIDED] Identity lookup:** prefer a documented ISRC from Spotify or Apple Music when available. Collapse catalog tracks sharing an ISRC to one recording by default, preserving their separate provider and release references; flag clear contradictory performance evidence for review. Otherwise, search with credited performer plus title, then use version, duration, date, release, and catalog clues to resolve the intended recording. Save the provider ID/URL and ISRC evidence. [Apple's ISRC endpoint](https://developer.apple.com/documentation/applemusicapi/get-multiple-catalog-songs-by-isrc) notes that one code can return multiple catalog songs, and [IFPI says](https://isrc.ifpi.org/why-use-isrc/when-not-to-assign) the same recording keeps its code across formats and ordinary remasters may keep it. Many historical/nonstreaming nominations may have no known ISRC. Neither an ISRC nor catalog availability is required to verify a corpus row.

The review sheet has optional `isrc`, `isrc_evidence_url`, `spotify_track_id`, `spotify_track_url`, `apple_music_song_id`, and `apple_music_song_url` columns. [Spotify Get Track](https://developer.spotify.com/documentation/web-api/reference/get-track) can return `external_ids.isrc` for an authenticated track ID; the field was [retained after March 2026](https://developer.spotify.com/documentation/web-api/references/changes/march-2026). The authenticated [Apple Music catalog API](https://developer.apple.com/documentation/applemusicapi/songs/attributes-data.dictionary) has a song `isrc` attribute. The public [iTunes Search API](https://performance-partners.apple.com/search-api) used by `collect_apple_identity_leads.py` does not expose ISRC, so this current lead pass cannot fill that column. Record the Apple Music song ID/URL alongside an ISRC if that API becomes available.

The next optional identifier pass should authenticate to Spotify or Apple Music, search the catalog by artist/title (or fetch a supplied provider track ID), retain plausible candidates, and extract ISRC only for a sufficiently identified recording. The review sheet currently has **zero ISRCs and zero Spotify or Apple Music song IDs**. Do not turn the public iTunes name-similarity leads directly into accepted ISRCs. Record provider misses and ambiguous matches; all such rows remain eligible for artist/title fallback when enrichment sources are benchmarked. Credentials must stay outside the repo.

## Current local checks

- 500 rows: 100 in each era, with 90 general and 10 hard cases per era.
- All year hints fall within their assigned era; no repeated artist/title string.
- No artist appears more than twice in the general cohort under the current exact artist spelling. Repeated titles across different artists exist (often intended cover/version stress cases) and still need recording-level duplicate review. Release concentration cannot be checked yet because release identities are not populated.
- 23 rows in the generated candidate TSV have an independent evidence link; other rows can still be queried and their missing links do not block the benchmark. The separate review worksheet contains additional manually researched evidence.
- Geographic hints are uneven: US/UK counts are E1 54/0, E2 48/15, E3 42/19, E4 44/19, E5 24/9. These are preliminary tags; this draft should not yet support geographic coverage conclusions.

## Before freezing or benchmarking

1. Run `check_query_readiness.py`, review obvious malformed rows and duplicates, and document the intended era/genre/region balance. Treat tags as provisional and allow unknowns in later analysis.
2. Have the developer review exact membership. Freeze a versioned input manifest before any scored-source lookup. Keep later replacements and focused follow-up sets separate; do not replace songs just because a tested source cannot find them.
3. During the benchmark, log raw retrieval outcomes for all 500. Adjudicate returned recording matches and a stratified correctness sample with independent evidence. Keep unresolved outcomes distinct from verified correct matches.

Rebuild locally with `python3 'Plan/Corpus Draft/build_manifest.py'`. This script makes no network requests.

The full execution sequence, source eligibility gates, dataset contract and outputs are in [Benchmark Handoff](../Benchmark%20Handoff.md). `python3 'Plan/Corpus Draft/check_readiness.py'` currently exits nonzero because many rows lack deep independent identity review; this no longer blocks an exploratory source benchmark.
