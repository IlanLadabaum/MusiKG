# Source capability audit — documentation pass

Status: [RESEARCHED] desk review, 2026-10-10. No 500-recording queries have been run. This document maps *advertised capabilities*, not measured coverage or approved app sources. A link establishes the documented feature only; where product reuse, caching, or API eligibility is unclear, that remains [OPEN]. The source-neutral benchmark and user-approved decisions are in [Data Source R&D](Data%20Source%20R%26D.md).

## What this pass changes about benchmark design

- [RESEARCHED] Query precision varies sharply. MusicBrainz supports typed entity search, ID lookup, linked-entity browsing and relationship includes; SecondHandSongs supports separate performance and work search with optional performer/date or work-credit filters; Wikidata supports arbitrary SPARQL patterns. Discogs is centered on release objects, and Wikipedia exposes article sections, requiring extraction and scope interpretation. Therefore count *requests needed to obtain a specific missing fact*, not just requests per song.
- [RESEARCHED] “Free” has several meanings: openly licensed data, free noncommercial API, free registered API, free manual lookup, and public webpages with no verified automated-use permission. These must remain separate in the practicality analysis.
- [PROPOSED] In addition to completeness, time, and cost, log **conditional retrieval feasibility**: can a source search a recording/work by stable identifier; fetch just that entity; request selected relationships/properties; and avoid downloading a whole release/article? This is an input to later source-order decisions, not a source-order decision itself.
- [PROPOSED] Retain observed source responses where allowed. If a term blocks retention, log that the response was received, endpoint, source ID, timestamp, byte count, permitted evidence/derived claims, and the exact retention constraint. An API that forbids durable facts may still be useful for live display, but its role in a persistent graph must be evaluated separately.

### Maturity and risk distinctions

- **Maintained official programmatic interfaces are documented** for MusicBrainz, Wikidata, The MLC, SecondHandSongs, Open Opus, ListenBrainz mapper, Spotify, AcoustID, Wikimedia/MediaWiki, Last.fm, TheAudioDB, and LoC. “Documented” alone does not guarantee uptime, complete fields, or public app eligibility.
- **Known stale/ended collections**: AcousticBrainz stopped new submissions; VIAF's posted bulk files state no updates since August 2024. DOREMUS update cadence still needs confirmation.
- **Access-sensitive candidates**: Discogs (persistent API-derived data; CC0 dump is a separate route), SecondHandSongs (written authorization for public tools), The MLC, Last.fm (prior contact for research), CISAC ISWC, and SoundExchange. Resolve applicable terms before automated large-scale querying.

## Non-graph information worth inventorying

The benchmark should retain useful scalar values and descriptive fields, with their source, date and rights, even when no graph edge is warranted. Their presence and completeness are unmeasured; they should be reported separately from credit coverage.

| Field family | Documented examples | Possible use / caution |
| --- | --- | --- |
| Identity and release detail | [MusicBrainz](https://musicbrainz.org/doc/MusicBrainz_Database) lists duration, release date and country, format, language, status, catalog number and barcode; Discogs also records release format and country. | Match versions, show a release timeline and explain why two apparently identical tracks differ. A release-market country is not an artist's origin. |
| Community description | [MusicBrainz](https://musicbrainz.org/doc/MusicBrainz_Database) has tags, aggregate ratings and annotations as supplementary data. [TheAudioDB's example response](https://www.theaudiodb.com/docs_json) includes genre, mood, style, theme, descriptions and music-video fields, often null. | Profiles, filters and discovery explanations; labels are subjective, text has different rights from factual metadata, and field sparsity needs measurement. |
| Acoustic properties | [AcousticBrainz](https://musicbrainz.org/doc/AcousticBrainz) has historic MBID-keyed spectral, rhythm, key/scale, mood and genre predictions under CC0; collection stopped in 2022. | Possible listening-pattern analysis or similarity explanations; model outputs are estimates and newer recordings may be absent. |
| Popularity/activity | [TheAudioDB's example response](https://www.theaudiodb.com/docs_json) contains listener, play, vote and score fields, but the displayed track has several null values. MusicBrainz has tag counts and rating counts. | Could help contextualize discoveries or stratify the benchmark; do not present user votes as sales or as global popularity without validating definition and coverage. |
| Commercial outcomes | [RIAA's searchable certifications](https://www.riaa.com/gold-platinum/) identify certified US titles. [RIAA's criteria](https://www.riaa.com/wp-content/uploads/2016/02/DIGITAL-SINGLE-AWARD-RIAA-AND-GRF-CERTIFICATION-AUDIT-REQUIREMENTS.pdf) combine downloads and streams into certification units. | A certification is a threshold achievement for an eligible title, not an exact sales count for a specific recording. No free reusable cross-territory sales feed has been verified. Treat this as a separate future source/access investigation. |
| Artwork and media | [Cover Art Archive](https://coverartarchive.org/) provides release images; TheAudioDB responses can include thumbnails and video references. | Enrich profiles and loading/exploration UI, subject to item-level image and media rights; do not count as credit graph coverage. |

[PROPOSED] Add a side-channel field-coverage report to the 500-recording benchmark: fraction with a value, fraction with conflicting values, completeness by era/region/genre, query cost and permitted retention. Keep exact sales, certifications, community popularity and a user's own listen weights conceptually separate.

## Provisional cross-source semantic type map

These are *candidate families* for comparison, not the graph schema. Keep raw role, source ID, subject entity, object entity, scope, version and evidence. Two similarly named roles merge only when they mean the same thing at the same scope. A release credit is not automatically a recording credit; a work composer is not a recording performer.

| Proposed family | Raw forms likely to map here | Valid subject/scope and non-equivalences |
| --- | --- | --- |
| `recording_performed_by` | MB recording→artist performer/vocal/instrument relationship; Discogs track `Vocals`, `Guitar`, `Performer`; Wikipedia track-specific personnel | Specific recording/track; retain instrument, vocal, date and role qualifiers. Discogs *release main credit* and album-level Wikipedia personnel stay `release_associated_with`, not this family. |
| `recording_produced_by` | MB recording producer; Discogs track `Producer`, `Co-producer`, `Executive Producer`; Wikipedia recording-specific production credits | Keep subroles distinct; album producer is release association unless source explicitly states track applicability. |
| `recording_engineered_by` | MB recording engineer/mix/mastering; Discogs track `Recorded By`, `Mixed By`, `Mastered By`; Wikipedia specific recording/session credits | Recording/session role, phase and location qualifiers matter. Mastering can be release/version-specific; do not collapse all “engineering.” |
| `work_written_by` | MB work composer/lyricist/writer; MLC/Songview/society writer/composer/lyricist; SecondHandSongs work credits; Wikipedia composition section | Work subject. Preserve writer subtype and ownership/rights confidence. A publisher or administrator is not a writer. |
| `work_published_or_administered_by` | MLC/society publisher/administrator/share; MB work publisher where represented | Rights relationship to work, with territory/effective-date/share qualifiers. Not a record label. |
| `recording_embodies_work` | MB recording↔work; MLC matched sound recording↔work; SecondHandSongs performance↔work | Link a specific recording/performance to composition; used to traverse writing credits without attributing them directly to a recording source. |
| `recording_derives_from` | MB cover/remix/sample relationships where typed; SecondHandSongs original/cover/sample; WhoSampled reference | Preserve `cover`, `sample`, `interpolation`, `remix`, `arrangement` separately. A shared work link alone does not establish a sample. |
| `release_contains_recording` | MB release track→recording; Discogs release tracklist→track; Spotify album→track | Release/version structure. Discogs track and Spotify provider track may not be resolved to the same canonical recording without evidence. |
| `release_issued_by_label` | MB release→label; Discogs release label/company; Spotify label if provided | Release scope; distinguish label, distributor, manufacturer and copyright holder. A record label relationship is not automatically recording-specific. |
| `entity_has_context` | Wikidata genre/place/date/member-of; Last.fm tags; TheAudioDB genre; LoC catalog terms | Typed attributes/context, with source and scope; a community tag is not a factual credit. Country of artist, recording site and release market are distinct. |
| `same_as_or_candidate_match` | ISRC, ISWC, MBID, Discogs ID, Wikidata ID, VIAF, Spotify ID, AcoustID, mapper confidence | An identifier link is identity evidence, not a credit. ISRCs can still lead to multiple catalog records and require version review. Preserve confidence/match method. |
